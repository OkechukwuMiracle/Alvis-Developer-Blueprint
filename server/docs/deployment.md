# Staging setup and rollback

Use a separate staging Supabase project and domain. No production resources are changed by the supplied configuration. No hosting service has been purchased or automatically provisioned.

1. Apply migrations 001–012 in filename order. Never apply the disposable `tests/integration/bootstrap.sql` to Supabase.
2. Enable public email/password signup and Confirm Email. Configure Auth SMTP, the confirmation/recovery templates from `supabase/templates`, Site URL, and exact redirect URLs `/auth/confirm` and `/auth/callback` for local and staging origins. Supabase Auth SMTP and application invitation SMTP are separate configurations.
3. Configure `server/.env.staging` from `server/.env.example` and public `client/.env.staging` from its example, with staging URLs, service/S3 credentials, the existing `OPENAI_MODEL_TEXT`, `OPENAI_MODEL_EMBED=text-embedding-3-small` (1536 dimensions), and a random `ALVIS_AUTH_FLOW_SECRET` of at least 32 characters. Never put secrets in build arguments or source control.
4. From the repository root, run `docker compose --env-file client/.env.staging -f compose.staging.yml build`, then `docker compose --env-file client/.env.staging -f compose.staging.yml up -d`. Use separate client and server environment files; route `/api/*` to server:4000 and other paths to client:3000 behind the configured HTTPS origin. The compose web port is bound to loopback; provide an HTTPS reverse proxy for the configured staging origin. Images include the blueprint prompts/schemas. The worker image installs FFmpeg/ffprobe and uses writable temporary storage. Separate media and learning worker processes share durable PostgreSQL leases.
5. Before using the environment, verify `docker compose -f compose.staging.yml exec media-worker ffmpeg -version`, `ffprobe -version`, web `/api/health`, real signup/verification/recovery, private recording upload/download, worker job completion, index dimension checks, and reviewer publication. Health only checks web configuration presence, not database/provider reachability.
6. Enable database backups, restrict service-role/S3 credentials, and configure access logs to exclude query strings and bodies. Never log passwords, invitation tokens, verification/recovery links or signed recording URLs. Application email/organization links use fragments and POST so their tokens do not enter ordinary URL access logs. The optional PKCE callback still requires query-string redaction. Disable email-provider link tracking on authentication and invitation links.

## Rollback

Stop the two worker services before changing versions. Retain the previous web/worker images and deploy them together. Do not reverse schema migrations or delete evidence to roll back a UI change. Test old-image compatibility against the current schema first; otherwise fix forward. Restore a staging backup only into a separate replacement staging project, then update server configuration and Auth redirects. Never reset production or a shared project to troubleshoot. In-flight jobs are lease-fenced and eligible jobs recover after expiry; exhausted jobs remain failed for explicit bounded recovery.

Container definitions are preparation, not proof of successful staging deployment. Record staging URL, image digest, migration versions, delivery result and end-to-end evidence in the release report after verification.
